## 1. 目的・背景

WinTask は「メイン担当を競って獲得する」グループ向けタスク管理アプリで、個人 Free／個人有料／法人プランと Stripe 課金基盤まで整っている。一方、集客導線が弱く、有料・法人機能へ到達するユーザーの母数が足りない。

WinDays は、それ単体で検索されて使われる価値を持つ**無料の個人向け予定管理・行動管理アプリ**として提供し、以下を狙う。「記録する手間」が行動記録アプリの最大の離脱要因なので、**予定を立てておけば記録が勝手に付く**ことを最大の差別化にする。

1. 「時間の使い方 可視化」「ワークライフバランス アプリ」「習慣 記録 無料」などの検索キーワードからの流入
2. 登録＝WinTask アカウントとすることで、誘導を「別アプリの案内」ではなく「同じアカウントで使える機能の解放」にする
3. WinDays で蓄積したタイムログ・習慣・日次サマリを、WinTask の個人タスク・日記・共有日報へそのまま接続し、**データの連続性**を乗り換え動機にする

既存資産の再利用（WinTask 側）:

| 既存資産 | WinDays での使い方 |
| --- | --- |
| Sanctum 認証・`POST /register` `POST /login` | 共通アカウント。そのまま利用 |
| `PlanService` / `config/plans.php`（個人 Free/Plus/Pro） | WinDays の無料制限（履歴日数・習慣数など）を同じカタログに追加 |
| 定期タスクの RRULE エンジン（毎週曜日・第n曜・土日祝スキップ・前後営業日シフト） | 習慣（定期行動）の発生日計算に流用 |
| `tasks:send-reminders`（15分ごと）とスケジューラ | 習慣・予定リマインダー、週次振り返りメールの送信基盤 |
| `diary_entries`（1日1件・タグ・気分・Free は直近7日） | WinDays の「1日サマリ」の保存先。**WinDays 側で新テーブルを作らず、WinTask 日記をそのまま使う** |
| `POST /me/tasks`（個人タスク） | 「明日もやる」→ 個人タスク化の導線 |
| `calendar_events`（予定・リマインダー） | 予定（プラン）の実体として共用（個人予定のみ。`days_category_id` を追加） |
| `landing/`（利用規約・プライバシー・特商法） | 法的ページの共通化 |

## 2. 用語定義

| 用語 | 定義 |
| --- | --- |
| ユーザー | WinTask と共通のアカウント（`users`）。WinDays から登録すると Free プラン |
| タイムログ（セグメント） | 「何時から何時まで、何をしていたか」の帯。1日は複数のセグメントで構成される。WinDays のコア記録 |
| カテゴリ | セグメントの分類（仕事・家事・レジャー・移動・睡眠・学習など）。色を持ち、ユーザーがカスタムできる |
| 領域（ドメイン） | カテゴリの上位区分。`work`（仕事）／`life`（プライベート・レジャー）／`rest`（睡眠・休息）の3種固定。バランス集計の軸 |
| 予定（プラン） | その日「こう過ごす」と事前に引いた帯。実体は WinTask の個人予定 `calendar_events`。カテゴリを持つ予定は**自動記録の対象**になる |
| 自動記録（オートトラック） | 予定の開始時刻にサーバーが自動でタイムログを開始し、終了時刻（＋猶予）で自動終了する仕組み。`source = auto` |
| 確認カード | 予定の開始・終了時刻にアプリ内（開いていれば）と Push 通知（閉じていれば）に出る「このまま／変更」の問いかけ。放置すると予定どおりに確定する |
| 猶予（グレース） | 開始確認・終了確認から自動確定までの待ち時間。既定 3 分・設定で 0〜15 分。猶予後の記録時刻は予定の開始・終了時刻（放置した猶予を実績にずらさない） |
| 変更（例外操作） | 予定と違う行動をしたときの操作。別カテゴリに切替・時刻ずらし・スキップ・続ける・早めに終了 |
| 繰り返し予定 | 「平日 9:00〜18:00 仕事」のように RRULE で繰り返す予定。ルーティン（テンプレート）と習慣の土台 |
| 習慣（定期行動） | 「毎朝ラン」「第2土曜は釣り」など繰り返し行う行動の定義。RRULE で表現し、達成／未達成を記録する |
| ストリーク | 習慣の連続達成回数 |
| 1日サマリ | その日のタイムログから自動生成する要約＋ひとことメモ。実体は WinTask の `diary_entries`（`team_id = null`） |
| チェックイン | レジャー用途の「どこで何をしたか」を写真1枚＋場所名で残す手動記録（GPS 常時追跡ではない） |
| ルーティン（テンプレート） | 「平日の基本パターン」など、予定の帯をまとめて登録する雛形。v0.3 では**繰り返し予定の束**として実現する（独立テーブルは持たない） |
| 導線 | WinDays から WinTask の機能へ移る UI（同一アカウントで、ログインし直しなしに遷移する） |

## 3. 想定ユーザー / 利用シーン

- **決まった時間割で働く人**（会社員・在宅勤務・シフト勤務）: 「平日 9:00〜18:00 仕事」を一度登録すれば、毎日の勤務時間が自動で記録され、残業・早退・休憩のズレだけを直す
- **仕事の時間管理をしたい個人**（フリーランス・裁量労働・リモートワーカー）: 1日の作業時間の内訳を把握し、予定どおり進んだかを振り返る
- **趣味・レジャーの記録を残したい人**: 週末の釣り・登山・旅行を写真1枚と場所で残し、「今年何回行けたか」を見返す
- **仕事と生活のバランスを見直したい人**: 週次・月次の「仕事:プライベート比率」の推移を見て働き方を調整する
- **習慣化したい人**: ランニング・学習・早起きなどのストリークと達成率を追う
- 上記が「チームでも共有したい」「タスクとして管理したい」と思った瞬間が、WinTask への誘導ポイント

## 4. 機能要件

### 4.0 中核コンセプト: 予定駆動の自動記録

行動記録アプリは「記録する手間」で離脱する。WinDays は **予定を立てておけば、予定どおりの時間は何もしなくても実績として記録される** ことを中核にし、ユーザーは予定と違ったときだけ操作する。

| 原則 | 内容 |
| --- | --- |
| 予定が既定で実績になる | カテゴリ付きの予定は、開始時刻に確認が出て、猶予（3 分）内に変更が無ければ**開始時刻ちょうど**から記録が始まる。終了も同様に、猶予内に操作が無ければ**終了時刻ちょうど**で終わる。例: 「9:00〜18:00 仕事」を登録しておけば、何もしなくても 9:00〜18:00 の〔仕事〕が記録される |
| 例外だけを操作する | 「今日は 10:00 から」「先に会議」「まだ続ける」「早めに終わる」「今日は休み」など、予定と違うときだけタップする |
| サーバーが真実 | 開始・終了の判定と記録の書き込みは Laravel のスケジューラ（毎分）が行う。アプリを閉じていても、通知が届かなくても、端末がオフラインでも、記録は予定どおり残る。アプリ内の確認カードと Push 通知は「変更するための入口」に過ぎない |
| 予定の無い時間は従来どおり | ワンタップ計測・帯入力・メモは Phase 1 のまま使える。自動記録は予定がある時間帯にだけ働く |
| 予定は WinTask と共通 | 予定の実体は WinTask の個人予定 `calendar_events`。WinTask で入れた予定にカテゴリを付ければ、それも自動記録の対象になる |

1 日の流れ（例: 平日 9:00〜12:00 仕事、12:00〜13:00 食事、13:00〜18:00 仕事）:

```
 8:55  アプリを開くと「今日の予定」3 件と、次の予定〔仕事 9:00〜12:00〕の開始カード
 9:00  開始確認カード「〔仕事〕を 9:00 から開始します」。アプリを開いていればカード、閉じていれば Push
       → 「OK」: その場で 9:00 開始の記録を作る
       → 3 分放置: 9:03 にサーバーが started_at = 9:00 で自動開始（source=auto）
       → 「変更」: 別カテゴリで開始／開始時刻をずらす／この予定をスキップ
12:00  〔仕事〕の終了確認カード。同時に〔食事〕を自動開始（次の予定が接している場合は切替）
13:00  〔食事〕終了 →〔仕事〕自動開始
18:00  〔仕事〕の終了確認カード「18:00 で終了します。続けますか？」
       → 「OK」: その場で 18:00 終了
       → 3 分放置: 18:03 に ended_at = 18:00 で自動終了（放置した 3 分は実績に含めない）
       → 「続ける」: 記録を継続。手動終了か止め忘れ通知（4 時間）まで続く。「+30 分」「+1 時間」の延長ボタンも出す
       → 「今終了」: 押した時刻で終了（残業の記録）
```

### 4.1 認証・アカウント（WinTask 共通）
- [x] メールアドレス + パスワードで新規登録（＝WinTask `users` に Free で作成）
- [x] ログイン / ログアウト（Sanctum トークン。WinTask `POST /api/v1/login` を利用）
- [x] **メール認証を必須化**（捨てアカウント・スパム対策）。既存ユーザーは移行時に `email_verified_at` を一括で埋め、再認証を求めない
- [ ] パスワードリセット（メール）
- [x] 登録時の同意: 利用規約・プライバシーポリシー（必須）／「WinTask などの関連サービスのお知らせを受け取る」（任意チェック・オプトイン）
- [ ] プロフィール（表示名・タイムゾーン。既定 `Asia/Tokyo`）
- [x] 既に WinTask を使っているユーザーは同じ資格情報でそのままログインできる
- （提案）Google ログイン（Phase 4）

### 4.2 カテゴリ管理
- [x] 初期カテゴリを自動投入（仕事／会議／家事／食事／移動／レジャー／学習／運動／睡眠／その他）。各カテゴリは領域（work/life/rest）と色を持つ
- [x] カテゴリの追加・名称/色/領域の変更・並び替え・アーカイブ（過去ログは残す）
- [ ] タグ（自由入力・複数）でカテゴリを横断した分類（Phase 3）

### 4.3 予定（プラン）— WinTask の個人予定と共用
- [x] 予定の帯を引く（タイトル任意・カテゴリ任意・開始/終了・メモ）。空のタイトルはカテゴリ名
- [x] タイムライン上で予定（左列）と実績（右列）を並べて表示
- [x] 予定を実績にコピー（「予定どおりだった」ワンタップ。`source=plan_copy`）。自動記録が入ると出番は減るが、過去日の後追い入力に残す
- [x] WinTask で入れた個人予定がそのまま表示され、WinDays 側からカテゴリを後付けできる。WinDays で立てた予定は WinTask のカレンダーに出る。チーム予定は対象外
- [ ] **自動記録の対象フラグ**（予定ごと。既定 ON。`days_auto_track`）。カテゴリの無い予定は対象外（一覧で「カテゴリ未設定・記録されません」と示し、タップで付けられる）
- [x] **繰り返し予定**（2026-09-12 実装。バックエンドは WinTask `feature/calendar-recurrence`、UI は予定シートの「繰り返し」欄と設定の一覧。初回設定ウィザードは未着手）: 「毎週月〜金 9:00〜18:00 仕事」「毎日 23:30〜7:00 睡眠」「第 2 土曜 釣り」を RRULE で登録。WinTask の定期タスクと同じ **「定義行（マスター）→ 生成済みの回」方式**で `calendar_events` 内に持ち、RRULE エンジン（`recurr`・曜日・第 n 曜・土日祝スキップ・営業日シフト）を流用して **14 日先まで具体的な予定行に展開**（`recurrence_parent_id` でマスターに紐づく。展開済みの回は個別に編集・スキップできる）。展開サービスは WinTask 側に置き、`days:expand-plans`（毎日 0:10 とマスターの変更時）が呼ぶ。編集の反映範囲は WinTask の予定仕様どおり「この予定のみ／以降すべて／すべて」。整合案は [§15.1](#151-決定済み)
- [x] **ルーティン**: 初回設定ウィザード（2026-09-15 実装。`/app/welcome`・`POST /days/onboarding`）で「平日の仕事」「睡眠」「休日の定番」の 3 問から繰り返し予定を一括作成。独立テーブルは持たず、繰り返し予定の束として扱う。完了は `users.days_onboarded_at`（スキップも完了扱い）
- [ ] **重なりの警告**: 同じ時間帯に自動記録対象の予定が 2 つある場合、作成時に警告（後から始まる方が切替として優先される）
- [x] 展開済みの回の編集・削除は反映範囲（この回のみ／以降すべて／すべて）を選ぶ。「この回のみ」の削除＝その日のスキップ（`POST /days/plans/{id}/skip`）
- [ ] 予定のリマインダー（開始 N 分前）は WinTask の `event_reminders` をそのまま使う（[§4.8](#48-リマインダー通知)）
- [ ] （Phase 3）WinTask の個人タスクをタイムラインへドロップして予定化する「タイムブロッキング」（[§4.13](#413-wintask-への導線)）

### 4.4 自動記録（オートトラック）— 本アプリの中核
**判定と書き込みはサーバー**（`days:auto-track`・毎分）。アプリは「見せる」「変更を受け付ける」だけ。

#### 開始
- [x] 予定の `starts_at` に開始確認カード／Push を出し、**猶予（既定 3 分・設定 0〜15 分）内に操作が無ければ `started_at = starts_at` で進行中セグメント**（`source=auto`・`plan_id`）を作る。「OK」を押せばその場で作る（時刻はどちらも予定の開始時刻）。ユーザーがそのときアプリを開いていなくても作る
- [x] 猶予中（9:00〜9:03）は進行中セグメントが無いが、「今日」画面では「〔仕事〕9:00 開始（確認中）」として記録中と同じ位置に表示する。猶予中に書いたメモは、セグメント作成時に `noted_at` が区間に入っていれば後から紐づける
- [x] 猶予後にアプリを開いた場合も、開始カードは「変更」できる状態で残る（`started_at` を今から／N 分後にずらす、別カテゴリに変える、スキップして削除）
- [x] 別の進行中セグメント（ワンタップ計測や前の予定の自動記録）があれば、`starts_at` で自動終了して切り替える（ワンタップの切替と同じ規則）。ただし進行中セグメントが**同じカテゴリ**なら終了せず、その記録に `plan_id` を付けて引き継ぐ（「8:50 から先に仕事を始めていた」場合に 9:00 で分断しない）
- [x] 予定の時間帯の一部が確定済みの記録で既に埋まっている場合、埋まっていない先頭から開始する。全部埋まっていれば何もしない（重複区間の禁止を守る）
- [x] 開始確認カード（アプリ内）／Push 通知（2026-09-14 実装）: 「〔仕事〕を 9:00 から開始します（〜18:00）」。操作は「OK」「変更」。**放置しても予定どおり記録される**
- [x] 「変更」の選択肢: 別カテゴリで開始（切替。予定はそのまま）／開始時刻を「今から」または「N 分後」にずらす（自動記録の `started_at` を書き換え）／この予定を今日はスキップ（記録を削除し、予定に `skipped` を記録）／さっきの記録を続ける（切り替えられた前の記録を再開し、この予定をスキップ）

#### 終了
- [x] `ends_at` に終了確認カード／Push（2026-09-14 実装）: 「〔仕事〕を 18:00 で終了します。続けますか？」。操作は「続ける」「今終了」「+30 分」「+1 時間」
- [x] **猶予（開始と同じ設定値）内に操作が無ければ `ended_at = ends_at` で自動終了**。「OK」を押してもその場で `ends_at` で終了。猶予後に閉じても終了時刻は予定の時刻（放置した 3 分を実績に含めない）
- [x] 「続ける」: 記録を継続。次の自動記録の開始、手動終了、止め忘れ通知（4 時間）のいずれかまで続く。「+30 分」「+1 時間」は予定の `ends_at` をその日だけ延ばし、延長後の時刻で再度確認する
- [x] 「今終了」: 押した時刻で終了（予定より早い終了）。猶予中に押せば `ended_at` は押した時刻
- [x] 次の自動記録対象の予定が `ends_at` に接している（または重なっている）場合は、終了確認を出さずに切り替える（「12:00 で〔仕事〕→〔食事〕に切り替えました」の 1 枚にまとめる）
- [x] 予定の途中でユーザーがワンタップで別カテゴリに切り替えた場合、自動記録はそこで終了し、以降その予定の終了処理は行わない（「戻る」は未実装）

#### 前提・設定・保護
- [x] 自動記録の ON/OFF（ユーザー設定 `days_auto_track`・既定 ON）と、予定ごとの ON/OFF（予定シートの「この予定を自動記録する」）
- [x] 猶予分数（0〜15・既定 3。開始・終了共通）。「今日は自動記録しない」（当日だけ停止するワンタップ。休みの日に予定どおり記録されるのを防ぐ）
- [x] 過去の予定（今日より前）は自動記録しない（実装: 終了時刻を過ぎた予定には run を作らない）。アプリを数日開かなくてもサーバーは毎分動くので取りこぼしは無いが、スケジューラが止まっていた区間は**復旧時に遡って補完しない**（誤記録を避ける。運用監視で検知する）
- [x] 確認カードはアプリ内では「今日」画面の最上部に固定表示。同時に複数出る場合は時系列で 1 枚ずつ。既読・操作済みは消える。過去のカードは通知履歴（設定内）から見返せる
- [x] Push 通知の操作ボタン: Android（Web Push / ネイティブ）は通知上で「続ける」「終了」を押せる（実装: 通知の操作は `/app?run=<id>&act=<action>` でアプリを開いて実行）。iOS の Web Push はボタン非対応のため通知タップでアプリを開いてカードを操作する（ネイティブ版では通知アクションに対応。[§16](#16-ネイティブ配信の方針)）
- [x] 通知が届かなくても記録は正しい、を設計の前提にする（Push の失敗・購読無し・機内モードで結果が変わらない）
- [x] 自動記録で作られた実績は編集画面に「予定から自動記録」と出す。手動で直したら `source` は `auto` のまま `edited_at` を持つ（計測用）

### 4.8 リマインダー・通知
通知は「操作の入口」であり、記録の成否には影響しない（[§4.4](#44-自動記録オートトラック-本アプリの中核)）。

| 種類 | タイミング | 経路 | 操作 |
| --- | --- | --- | --- |
| 開始確認 | 予定の開始時刻 | アプリ内カード＋Push | OK／変更 |
| 終了確認 | 予定の終了時刻（猶予あり） | アプリ内カード＋Push | 続ける／今終了／+30 分／+1 時間 |
| 切替通知 | 接した予定の切替時 | アプリ内カード＋Push（設定で OFF 可） | 戻す |
| 止め忘れ（✅ 2026-09-16） | 「続ける」後やワンタップ計測が閾値（既定 4 時間・1〜12 時間・OFF。`users.days_overrun_hours`）を超えたとき。再通知は間隔を倍にして最大 3 回（H・3H・7H）。`days:notify-overrun`（5 分ごと） | Push→無ければメール | 終了／続ける |
| 今日の予定 | 朝の設定時刻（既定 7:30・OFF 可） | Push（無ければ送らない） | 開く |
| 予定の N 分前 | 予定ごと（WinTask の `event_reminders` を共用） | Push→無ければメール | 開く |
| 未記録の夜間リマインダー | 予定が無く記録も無い日の設定時刻 | Push→無ければメール | 開く |
| 週次振り返り | 毎週日曜夜（時刻設定可） | メール | 開く |

- [x] 経路は **Web Push（PWA）を第一**（2026-09-14 実装: VAPID・`days_push_subscriptions`・`SendDaysPush` ジョブ・404/410 で購読削除・設定画面で購読／解除／テスト送信）。購読が無い端末にはメール（開始・終了確認はメールに落とさない。未実装）。購読の案内は「今日に予定があり未購読のとき」に「今日」画面へ 1 回出す
- [x] 送信はスケジューラ（`days:auto-track`・毎分）からキュー（`SendDaysPush`）へ。送信履歴は `days_notifications.pushed_at`。止め忘れ通知は `days:notify-overrun`（5 分ごと。Push が無ければメール `DaysOverrunNotification`。通知からの終了は `POST /days/segments/{id}/stop` の `notification_id` で `acted_at` に記録）
- [ ] 無料ユーザーのメール送信数に上限（1 日 10 通）。Push は上限の対象外

### 4.9 ダッシュボード（このアプリの顔）

### 4.13 WinTask への導線

- [ ] **「タスクにする」**: 習慣（繰り返し予定）を WinTask の定期タスクへ変換する案内。習慣は無料、定期タスク化は有料（`recurring_enabled`）
- [ ] **「チームで共有」**: 1 日サマリを共有日報にする操作。WinTask の日記共有へ誘導
- [x] **シームレスなログイン引き継ぎ**: `POST /auth/handoff` → 遷移先で `POST /auth/handoff/exchange`（有効 60 秒・1 回限り）
- [ ] 導線の表示は「共有したくなった瞬間」「繰り返したくなった瞬間」「タスクを時間に落としたくなった瞬間」に限定し、常時バナーは出さない

## 7. 技術構成

### 7.1 フロントエンド（`/var/www/WinDays`・本リポジトリ）
- React + Vite + TypeScript + Tailwind CSS（WinTask `web/` と同じバージョン系に揃え、型定義・API クライアントの流儀を共有）
- 状態: TanStack Query（サーバ状態）＋ Zustand（UI 状態・進行中セグメント）
- ルーティング: react-router。フォーム: react-hook-form + zod
- タイムライン描画: DOM（div 帯）＋ Pointer Events。Canvas は不要
- グラフ: Recharts（円・積み上げ棒・折れ線）
- PWA: `vite-plugin-pwa`（Service Worker・マニフェスト・オフラインキュー）。オフライン入力は IndexedDB（idb）に保持
- ネイティブ（Phase 4）: 同じビルドを Capacitor で包む（`@capacitor/core`・`local-notifications`・`push-notifications`）。ネイティブ固有の分岐は `Capacitor.isNativePlatform()` に閉じ込める（[§16](#16-ネイティブ配信の方針)）
- 日付: date-fns（`Asia/Tokyo` 固定から開始し、タイムゾーンはユーザー設定で拡張）
- 配信: 静的ビルドを Nginx で `days.winroad.org` から配信。LP・解説ページは同じビルドに含める（SSR は不要。SEO 対象ページはプリレンダー）

### 7.2 バックエンド（WinTask リポジトリ `backend/`・Laravel）
- 既存の Sanctum 認証・`PlanService`・スケジューラ・メール送信をそのまま利用
- 追加: WinDays 用マイグレーション（[§8](#8-データモデル)）、`Api/Days/*Controller`、Policy、`days:*` artisan コマンド（**自動記録 `days:auto-track`（毎分）**、繰り返し予定の展開、止め忘れ通知、週次振り返りメール、休眠整理）
- **スケジューラの毎分実行が必須**（cron の `schedule:run`）。自動記録の遅延は最大 60 秒。スケジューラ停止は監視し、止まっていた区間は遡って補完しない
- API ホスト: `api.days.winroad.org` の Nginx vhost（`deploy/nginx/api.days.winroad.org.conf`）を追加し、既存 `api.task.winroad.org` と同じ Laravel を指す。Let's Encrypt 証明書を発行
- CORS: `config/cors.php` の `allowed_origins` に `https://days.winroad.org` を追加
- WinDays のフロントは `VITE_API_BASE_URL=https://api.days.winroad.org/api/v1` を使う
- 変更: メール認証必須化（既存ユーザーは一括 verified）、`throttle` 追加、ログイン引き継ぎ API、`DELETE /me`、`personalCatalog()` への項目追加と `diary_history_days` Free=28
- **作業は WinTask 側の安全規則どおり worktree（`/var/www/WinTask-rf` 方式）で行い、デプロイスクリプト `deploy/windays-phaseN-deploy.sh` を用意する**

### 7.4 メール配信基盤

本番の WinTask は現在 `MAIL_MAILER=log`・`QUEUE_CONNECTION=sync` で、メールを実送信していない。WinDays はメール認証・リマインダー・週次振り返りがコア機能のため、**Phase 0 で実送信基盤を整える**。

当初は Xserver（`winroad.jp`）の SMTP を予定したが、**Xserver のサーバーが VPS の IP（160.251.215.3）からの接続を全ポートで遮断している**ことが判明（2026-09-09。Gmail 等の SMTP には接続できるため VPS 側の制限ではない）。サポートへ解除依頼はするが、通知メールの基盤を外部の遮断判断に委ねないため、**VPS 自身の Postfix から送る構成を本線**とする。

| 項目 | 決定 |
| --- | --- |
| 送信経路 | **VPS 上の Postfix**（`mail.winroad.org`）。Laravel からは `sendmail` トランスポート（`/usr/sbin/sendmail -bs -i`）で渡す。**2026-09-09 に本番 `.env` を切替え、Gmail 宛テスト送信で SPF / DKIM / DMARC すべて pass を確認済み。**`127.0.0.1:25` への SMTP は STARTTLS の証明書名不一致で失敗するため使わない。開発・検証は引き続き `log` |
| 送信ドメイン・From | `no-reply@winroad.org`。Reply-To は `info@winroad.org`（既存の受信箱） |
| 送信ドメイン認証（設定済み） | SPF `v=spf1 a mx ip4:160.251.215.3 -all`／DKIM selector `mail`（opendkim が Postfix の milter として稼働、公開鍵は DNS 公開済み）／DMARC `p=none`（レポート先 `info@winroad.org`）／PTR `mail.winroad.org`。運用が安定したら DMARC を `p=quarantine` へ |
| 外向き 25 番 | ConoHa VPS から Gmail の MX へ 25 番で接続できることを確認済み |
| Postfix 側の追加 | `no-reply@winroad.org` を `virtual_alias` で `info@winroad.org` に転送（バウンスの受け皿） |
| Laravel 設定 | `MAIL_MAILER=sendmail`、`MAIL_FROM_ADDRESS=no-reply@winroad.org`。手順は [メール設定手順.md](メール設定手順.md) |
| 送信量の見込み | 無料ユーザー 1,000 人の場合: 週次振り返り 1,000 通/週 ＋ リマインダー約 400 通/日 ＝ **月 1.6 万通前後、1 日 500 通前後** |
| キューとレート制限 | `QUEUE_CONNECTION=database` に切替え、`php artisan queue:work` を systemd で常駐。メール送信ジョブに **1 分あたり 20 通**のレート制限ミドルウェアを付け、週次振り返り 1,000 通は約 1 時間かけて送る（受信側の Gmail 等でのレピュテーション保護）。`days:weekly-digest` はユーザー単位でジョブを投入する |
| バウンス・苦情 | `info@winroad.org` に届くバウンスメールを Dovecot の IMAP（localhost:993）から定期取り込み（`days:ingest-bounces`・1 時間ごと）し、ハードバウンス／苦情のアドレスは `users.mail_suppressed_at` を立てて送信停止。送信失敗は `failed_jobs` で拾って再送 |
| 配信停止 | 全メールに署名付き URL の配信停止リンク（`List-Unsubscribe` ヘッダも付与） |
| 監視 | Postfix のキュー滞留（`mailq`）と `/var/log/mail.log` の bounce/deferred を日次で確認。Gmail Postmaster Tools に `winroad.org` を登録し、レピュテーションを見る |
| SES への移行 | **1 日 5,000 通を超えたとき、または到達率の問題（迷惑メール判定・IP レピュテーション低下）が出たとき**に Amazon SES へ移行。Laravel のメーラーは `.env` の切替のみで移行できる |

## 8. データモデル

WinTask の既存テーブル（`users` / `calendar_events` / `diary_entries` / `tasks` / `recurring_tasks` / `subscriptions`）はそのまま使い、WinDays 固有のものは `days_` プレフィックスで追加する。

```
users (既存 + days_auto_track, days_end_grace_minutes, days_paused_on, timezone …)
  ├─< days_categories (id, user_id, name, color, domain[work/life/rest], sort, archived_at)
  ├─< calendar_events (WinTask 既存。個人予定 team_id=null を「予定」として共用)
  │     + days_category_id[nullable]   … 実装済み（2026-09-11）
  │     + days_auto_track[bool=true]   … 自動記録の対象
  │     + recurrence_parent_id[nullable] … 繰り返し予定から展開された回。マスター行は rrule を持つ
  │     + original_starts_at[nullable], is_exception[bool] … 個別変更した回（Google の例外インスタンスと同型）
  │     + is_habit[bool], habit_target_minutes[nullable] … 習慣として数える
  │     └─< days_plan_runs (id, calendar_event_id, user_id, segment_id[nullable],
  │                         state[pending/starting/started/ending/ended/skipped/changed/extended],
  │                         started_notified_at, end_notified_at, grace_until,
  │                         extended_until[nullable], resolved_at, resolved_by[auto/user])
  ├─< days_segments   (id, user_id, category_id, plan_id[nullable→calendar_events],
  │                    started_at, ended_at[nullable=進行中], note,
  │                    source[tap/manual/plan_copy/auto], edited_at[nullable], client_uid)
  │     ├─< days_segment_tag (segment_id, tag_id)
  │     └─  days_checkins (id, segment_id, place_name, photo_path, lat, lng, taken_at)
  ├─< days_memos      (id, user_id, segment_id[nullable], noted_at, body)
  ├─< days_tags       (id, user_id, name)
  ├─< days_habit_logs (id, calendar_event_id[親], occurred_on, status[done/skipped/missed],
  │                    minutes, segment_id[nullable])
  ├─< days_notifications (id, user_id, kind[start/end/switch/overrun/morning/reminder/…],
  │                    calendar_event_id[nullable], segment_id[nullable], channel[push/mail/inapp],
  │                    sent_at, acted_at[nullable], action[nullable])
  ├─< days_push_subscriptions (id, user_id, endpoint, p256dh, auth, user_agent, last_used_at)
  ├─< days_reminders  (id, user_id, kind[morning/daily_empty/weekly_digest/overrun],
  │                    minutes_before, time_of_day, enabled, last_sent_at)
  ├─< funnel_events   (id, user_id[nullable], name, props(json), created_at)
  └─  diary_entries (既存・1日サマリの保存先。team_id=null)
```

## 12. 受け入れ基準（抜粋）

- **自動記録（基本）**: 「9:00〜18:00 仕事」の予定を登録し、その日アプリを一度も開かなかった場合、9:03 に進行中セグメントが `started_at = 9:00` で作られ、18:03 以降に `source=auto`・9:00〜18:00 の〔仕事〕セグメントが 1 本存在する。9:00〜9:03 と 18:00〜18:03 の放置時間は実績に含まれない
- **開始の変更**: 9:00 の開始カードで「変更 → 会議で開始」を選ぶと、9:00〜の進行中セグメントが〔会議〕で作られ、予定〔仕事〕はそのまま残る。9:10 に開いて「変更 → 今から」を選ぶと、9:03 に自動で作られた記録の `started_at` が 9:10 に直る。いずれも予定どおり率には「変更」として数えられる
- **終了の延長**: 17:58 に終了カードで「続ける」を押すと 18:03 を過ぎても記録が続き、19:10 に「終了」で `ended_at = 19:10` になる。「+1 時間」を押すと 19:00 に再度終了カードが出る
- **早い終了**: 17:30 に「今終了」を押すと `ended_at = 17:30` で確定し、18:00 の終了カードは出ない
- **接した予定の切替**: 「9:00〜12:00 仕事」「12:00〜13:00 食事」で、12:00 に〔仕事〕が終了し〔食事〕が開始する。終了カードは出ず、切替通知が 1 枚出る
- **先に始めていた**: 8:50 にワンタップで〔仕事〕を開始していた場合、9:00 の自動記録はその記録を引き継ぎ（分断しない）、18:00 の終了処理はその記録に対して行われる
- **今日は自動記録しない**: 設定で「今日は自動記録しない」を押した日は、確認カードも自動記録も発生しない
- **通知に依存しない**: Push を購読していない端末・機内モードの端末でも、上記の記録結果は同じ
- WinDays で登録したユーザーが、同じメール/パスワードで `task.winroad.org` にログインでき、Free プランの上限（Team×1・招待1名）が適用されている
- 1日に 30 セグメントを帯入力しても、重複区間が作れず、日跨ぎのセグメントが両日の集計に正しく按分される
- 「今から仕事」→ 別カテゴリをタップしたとき、前のセグメントが自動終了し、新しい進行中セグメントが 1 つだけ存在する
- 繰り返し予定「毎月末営業日」が土日祝を避けて正しい日に展開され、その回の実績が目標分数以上ならストリークに反映される
- 1日サマリを保存すると WinTask の日記画面に同じ内容が表示される（`team_id = null`）
- Free ユーザーがダッシュボードで 5 週前を選ぶと、入力は妨げられずロック表示とアップグレード案内が出る
- 「明日もやる」で作成した個人タスクが WinTask の「自分の担当」に現れる
- 週次振り返りメールに配信停止リンクがあり、停止後は送信されない
- ワンタップ計測を 4 時間放置すると、Web Push を購読した端末には通知が届き、購読が無いユーザーにはメールが届く。通知の「終了」で記録が閉じ、同じ記録への通知は間隔を倍にして最大 3 回で止まる
- ホーム画面アイコンの長押しメニューに「記録を終了」とクイック枠 3 件が出て、選ぶと 2 秒以内に記録が開始または終了し、「今日」に遷移してトーストが出る
- `/quick?start=仕事` を未ログインで開くと、ログイン後に同じ操作が実行される
- オプトインしていないユーザーに WinTask のお知らせメールが届かない
- 登録 API に 1 分間に 6 回アクセスすると 429 が返る

## 13. あえて入れないもの

| 機能 | 理由 |
| --- | --- |
| バックグラウンド GPS 追跡 | ストア審査・電池・プライバシーの三重苦。WinTask の位置記録要件定義書自身が警告。法人向け位置記録とは切り離す |
| SNS 的な公開・フォロー・共有 | 行動記録は機微情報。既定完全非公開とし、共有は WinTask の役割に限定することで設計とプライバシーポリシーを簡潔に保つ |
| 独自の日記テーブル | WinTask `diary_entries` で足りる。二重化するとデータ連続性という最大の武器を失う |
| 独自の課金・決済 | WinTask の Stripe をそのまま使う |
| ネイティブアプリの別実装（Flutter 等） | 同じ React コードを Capacitor で包んで配信する（[§16](#16-ネイティブ配信の方針)）。2 本のコードベースは保守できない |
| 端末側だけで完結する自動記録 | 端末のタイマーやバックグラウンド実行に頼ると、OS の省電力・アプリ終了で取りこぼす。判定はサーバーに置く |
| 位置情報・Wi-Fi・Bluetooth による自動判定 | 「会社に着いたら仕事開始」は魅力的だがバックグラウンド GPS と同じ問題を抱える。予定ベースの自動記録で 9 割を賄い、残りは例外操作にする |

## 14. 追加提案（標準仕様＋α）

自動記録を軸にしたときに効く機能。番号順が優先度の目安。

1. **予定の自動調整提案**（Phase 3）: 実績が予定と同じ方向にズレ続ける予定（例: 仕事の終了が 5 日連続 +30 分）に「終了を 18:30 にしますか？」と提案し、ワンタップで繰り返し予定を直す。予定が実態に近づくほど例外操作が減り、自動記録の精度が上がる
2. **初回設定ウィザード**（Phase 2）: 「平日の仕事は？」「睡眠は？」「休日の定番は？」の 3 問で繰り返し予定を作る。登録直後から自動記録が動き、翌日には記録が付いている状態にする。オンボーディング完了率と翌日再訪に直結
3. **朝の「今日の予定」通知**（Phase 3）: 7:30 に「今日は 仕事 9:00〜18:00・ジム 19:00〜20:00」。予定の確認と変更をその場でできる。再訪の日次トリガー
4. **延長のクイックボタン**（Phase 2）: 終了カードの「+30 分」「+1 時間」。残業・延長を 1 タップで実績に反映し、「続ける」後の止め忘れを減らす
5. **タイムブロッキング**（Phase 3）: WinTask の期限付きタスクを「今日の予定」にドロップして時間を確保する。実績が確定したらタスクに作業時間を書き戻す。WinTask 導線の中で最も自然な入口
6. **隙間の自動〔移動〕**（検討）: 場所の違う予定の間（例: 会社→ジム）に「移動」を自動で挟む提案。位置情報は使わず、予定の `location` の違いだけで判定
7. **予定どおりバッジ・週次スコア**（Phase 3）: 「今週の予定どおり率 88%」を週次メールとダッシュボードに。年間ヒートマップ（習慣達成・レジャー日）は画像書き出し可
8. **記録中の可視化（ネイティブ）**（Phase 4）: iOS Live Activities／Android 常駐通知で「〔仕事〕記録中 2h15m」とロック画面に出し、そこから「終了」「切替」ができる
9. **ホーム画面ウィジェット**（Phase 4）: 今日の予定 3 件と次の確認時刻を表示
10. **今日の一言 AI 要約**（将来）: 1 日サマリの自動下書きを Claude で自然文に。無料は週次のみ、日次は有料
11. **バランス目標**: 「仕事は週 40h 以内」「運動は週 3 回」の目標と達成度
12. **WinTask 側の「WinDays で記録」ボタン**: 完了タスクからタイムログを 1 セグメント作る逆導線

| データ表現 | `calendar_events` に **マスター行**（`rrule` 非 null。`starts_at/ends_at` は初回の時刻、`dtstart` 相当）と **展開済みの回**（`recurrence_parent_id` = マスター id、`original_starts_at` = RRULE 上の本来の開始、`is_exception` = 個別変更あり）を持つ。スキップした回は soft delete（Google の `status=cancelled` インスタンスと同型）。WinTask の定期タスク（`recurring_tasks` → 生成済み `tasks`）と同じ構図 |
| 展開の責務 | WinTask 側に `CalendarRecurrenceService`（`recurr` と祝日・営業日シフトを流用）を新設し、**個人・チーム予定の両方で使う**。展開ウィンドウは 14 日先まで（WinDays の自動記録に十分。Google 連携時は Google 側の展開を尊重）。WinDays の `days:expand-plans` はこのサービスを呼ぶだけ。展開は冪等（`recurrence_parent_id` + `original_starts_at` で一意） |
| 一覧 API | `GET /me/events`・`teams/{team}/events`・`/days/plans` は**マスター行を除外**し、展開済みの回だけ返す（`whereNull('rrule')`）。マスターは `GET /events/{id}` と繰り返し管理画面でのみ扱う |
| 編集の反映範囲 | `scope=this\|following\|all`。`this` は該当回を `is_exception=true` にして直す。`following` はマスターの `rrule` に `UNTIL` を切り、新しいマスターを作って再展開。`all` はマスターを直して未来の未変更の回を再展開（`is_exception` の回は保持）。WinTask 予定仕様 5.1「この予定のみ／以降すべて」に「すべて」を加える |
| Google 連携（WinTask Phase 2）との対応 | マスター ↔ Google の繰り返しイベント（`recurrence` フィールド）、展開済みの回 ↔ `instances`、`is_exception` ↔ 個別変更インスタンス、soft delete ↔ `cancelled`。`google_event_mappings` はマスターと例外の回だけ持てばよい |
| WinDays 固有の列 | `days_category_id`・`days_auto_track`・`is_habit`・`habit_target_minutes` はマスターに置き、展開時に回へコピー（回ごとの上書き可）。WinTask の画面では無視される |
| 実装の置き場 | マイグレーション・モデル・展開サービスは WinTask リポジトリ（`feature/calendar-recurrence`）。WinDays はその上に `days:expand-plans` と UI を載せる。WinTask 側の React／Flutter に繰り返し UI を出すのは WinTask の Phase 1 後半でよい（API は先に揃う） |
| 影響範囲 | WinTask 既存テスト（`CalendarEventTest`）に「マスター行は一覧に出ない」「展開済みの回は編集できる」を追加。既存の単発予定は `rrule` null のまま無影響 |

## 16. ネイティブ配信の方針

**結論: Flutter などで別に作る必要はない。** 同じ React（Vite）コードを **Capacitor** で包み、iOS / Android のネイティブアプリとして App Store / Google Play に配信する。

| 観点 | PWA（現行） | **Capacitor（採用）** | Flutter で別実装 |
| --- | --- | --- | --- |
| コードベース | 1 本 | **1 本**（Web と共通。ネイティブ固有はプラグイン呼び出しだけ） | 2 本（React と Dart。機能追加のたびに二重作業） |
| ストア配信 | 不可（ホーム画面追加のみ） | **可** | 可 |
| 予定時刻の通知（アプリを閉じていても） | サーバーからの Web Push。iOS は 16.4 以降・ホーム画面追加が条件。**iOS の Web Push は操作ボタン非対応** | **ローカル通知を端末側で予定時刻にスケジュール**（オフラインでも出る）＋ APNs/FCM Push。**両 OS で通知上の「続ける」「終了」ボタン**が使える | 同左 |
| 記録中の常時表示 | 不可 | iOS Live Activities／Android 常駐通知（プラグインまたは小さなネイティブコード） | 同左 |
| ウィジェット | 不可 | 可（ネイティブ側に小さな実装が要る） | 可 |
| バックグラウンド実行 | 不可 | 限定的（OS 依存）。**自動記録の判定はサーバーに置くので不要** | 同左 |
| 学習・保守コスト | 無し | 小（Capacitor の設定・ストア申請） | 大 |

- **なぜ成立するか**: 自動記録の判定・書き込みをサーバーに置いた（[§4.0](#40-中核コンセプト-予定駆動の自動記録)）ため、端末側に求めるのは「通知を出す」「操作を API に送る」「画面を出す」だけ。これは WebView で十分で、ネイティブの描画性能や複雑な OS 連携を必要としない
- **Web 版との関係**: 同じ URL の SPA をネイティブでは同梱（ローカル読み込み）。API・認証（Sanctum トークン）・画面はすべて共通。ストア版だけの機能（ローカル通知の操作ボタン・Live Activities・ウィジェット）は `Capacitor.isNativePlatform()` で分岐
- **通知の二重化**: ネイティブ版は「予定の開始・終了時刻」を端末のローカル通知にも登録する（サーバー Push が遅れても出る）。同じ予定の通知はサーバー側の `days_notifications` と端末側の通知 ID を突き合わせて片方を消す
- **PWA の限界の整理**: iOS の PWA は Web Push に操作ボタンが無く、ローカル通知のスケジュールもできない（Notification Triggers API は廃止）。ただし「通知が出なくても記録は正しい」設計なので、**PWA でも中核の価値は成立する**。ストア版は体験の上乗せと集客チャネルの追加
- **WinTask の Flutter アプリとの関係**: WinTask は Flutter を持つが、WinDays は React で作り直しているため Flutter を選ぶ理由が無い。将来 WinTask の React 版（`web/`）も同じ方法でストア配信できる
- **費用・準備**: Apple Developer Program 年 99 USD、Google Play 初回 25 USD、iOS ビルドには Mac（Xcode）が必要。審査は「Web サイトをそのまま包んだだけ」と見なされると却下されるため、ローカル通知・Live Activities・ウィジェットなどネイティブ機能を入れた状態で申請する
- **着手時期**: Phase 4。Phase 2 の自動記録が Web で動き、Phase 3 の計測で継続率が見えてから

### 16.1 開始・終了時刻の位置情報の自動取得について

**結論: 「予定の開始・終了時刻に、ユーザーが何も操作しなくても GPS を取る」機能は入れない。** iOS では技術的に成立せず、Android でも常時位置情報の権限が要るため、[§13](#13-あえて入れないもの) のバックグラウンド GPS 禁止と同じ問題を抱える。代わりに、**ユーザーが確認カードや通知を操作した瞬間の 1 点だけ**を任意で残す「位置スタンプ」を Phase 4（ネイティブ）の候補にする。

| 方式 | PWA | Capacitor（使用中のみ許可） | Capacitor（常に許可） | 評価 |
| --- | --- | --- | --- | --- |
| 予定時刻にサーバーが自動確定するとき（無操作）に位置を取る | 不可（Service Worker から位置情報は取れない） | 不可（アプリが起動していない） | iOS: 不可に近い（時刻指定のバックグラウンド起動が無い。Background Fetch は時刻を選べない）／Android: 可（正確なアラーム＋フォアグラウンドサービス。Play の常時位置情報ポリシー審査あり） | **採用しない**。OS 間で挙動が揃わず、審査・電池・プライバシーの負担が大きい |
| 通知の操作ボタン（続ける／終了）を押した瞬間に取る | 不可（iOS は操作ボタン非対応。Android も SW から位置は取れない） | iOS: アプリを前面に出す設定なら可／Android: 可 | 可 | **位置スタンプの候補**。「終了」を押した場所が残る |
| アプリ内の確認カードを押した瞬間に取る | 可（`navigator.geolocation`・許可ダイアログあり） | 可 | 可 | **位置スタンプの候補**。PWA でも成立する唯一の方式 |
| ジオフェンス（会社に着いたら〔仕事〕開始） | 不可 | 不可 | 可（`Region monitoring`／`Geofencing API`） | 魅力はあるが**常時許可が前提**。§13 の方針どおり入れない。将来やるなら明示的オプトインの別機能として再検討 |

- **位置スタンプ（Phase 4 候補・任意・既定 OFF）**: 設定で ON にすると、確認カード・通知の操作時に 1 点だけ緯度経度を取り、その実績に `lat/lng/captured_at` として保存する（`days_checkins` の仕組みを流用）。無操作で自動確定した実績には位置が付かない（付かないことを画面に示す）。用途は「その日どこで働いたか」の記憶補助であり、勤怠の証跡には使わない
- **勤怠・証跡が目的の場合**: WinTask の法人向け位置記録（`docs/位置記録(GPS足跡)_要件定義書.md`）の領域であり、WinDays には持ち込まない
- **iOS の補足**: 「常に許可」を取っても、時刻指定でアプリを起こす API は無い。`significant location change` や `region monitoring` は「場所が変わったとき」に起きるもので、「9:00 になったとき」には起きない。よって iOS で「9:00 に無操作で位置を取る」は設計として成立しない
